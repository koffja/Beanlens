# ADR 0004：会话状态机、放弃机制、400 拒收重报规则

- 状态：已接受（2026-10-23）；**v1 网络上报部分暂不实施，用 mock 客户端本地验证**（2026-10-24，见 ADR 0003 / 0005）
- 影响范围：固件主干逻辑、UI 流程、队列状态枚举、幂等重试策略、操作员交互

> **v1 实施状态（2026-10-24）**：C6 网络桥延后，v1 不做真实上传。下文「上报 / 上传中 / 已入库」在 v1 对应「本地保存 / saving / saved」；
> 400 / 403 / 429 / 5xx 的分类、指数退避、幂等键、断电恢复、放弃机制的决策**全部保留**，由 `report.py` 的 mock 客户端模拟响应来验证，P2 切真实网络时只替换 HTTP 客户端。

## 背景

从「停止」到「入库」之间有多个岔口：补豆、放弃、改数据重报、拒收后人工修正、配额用尽、断电恢复。这些决策决定固件的状态机复杂度与队列持久化格式。

## 决策

### 1. 会话状态机

```
待机 ──开始──▶ 扫描中 ──停止──▶ 结果待确认 ──上报──▶ 排队待传 ──▶ 上传中 ──▶ 已入库
                    │                  │                              │
                    │                  └──放弃──▶ 已放弃（本地留档）    └──失败──▶ 待重试 / 被拒(人工)
```

### 2. 四个关键岔口

| # | 岔口 | 选择 | 理由 |
|---|---|---|---|
| 1 | 结果页能否「继续扫描」补豆 | **不能，只能新开会话** | `captured_at`、`duration_s`、计数已冻结，再补豆会让同一记录数据前后矛盾 |
| 2 | 「放弃」是否存在 | **有，二次确认 + 本地留档** | 现场必有"豆洒了/装错了"；不给按钮就会拔电源，更糟 |
| 3 | 放弃的记录怎么处置 | **保留 7 天不进队列** | 标记 `discarded`、永不上报，但留档供事后对账 |
| 4 | 400 拒收后能否改数据重报 | **能，但复用同一 `operation_id`** | 服务端未落库，同 ID 重发不会重复；换 ID 可能在超时误判场景产生重复记录 |

### 3. 额外约定

- **上传成功后**：本地保留记录元数据但删证据图（图占空间，元数据用于对账）；
- **403 配额用尽**：不删、不重试、屏上显示"额度已用尽" + 队列条数，等额度恢复或换账号（受 ADR 0003 约束：有未上传队列不许解绑）；
- **NTP 对时失败**：不阻断扫描，`captured_at` 用本机钟并打 `metadata.clock_unreliable: true` 标。

### 4. 断电与崩溃恢复

| 决策 | 选择 | 理由 |
|---|---|---|
| 扫描中掉电能否恢复成可上报记录 | **恢复为「未完成」但不可上报**，只能看/丢弃 | 分母（豆粒总数）不完整、`duration_s`/`captured_at` 不可信，不能塞进正式记录 |
| 落盘频率 | **每 30 颗或每 5 秒 checkpoint，先到先写** | 只停止时写 = 断电全丢；每次变化 = TF 与 CPU 无谓 IO；checkpoint 让"最多丢 30 颗"可解释 |
| 写盘方式 | **临时文件 + 原子 rename + 保留 .prev** | 覆写中断会得到半个 JSON；原子替换保证"要么旧要么新" |

启动时发现上次非正常退出 → 待机页横幅提示"上次扫描未完成（12:31，约 340 颗），查看 / 丢弃"，可滑走、不阻断正常使用。

### 5. 队列容量与边界

- **队列双阈值**：条数 100 **且** 证据图总量 ≤ 500MB（v1 无图，此项为预留），任一触顶阻断新扫描并提示"请清理/恢复网络"；
- **未完成会话**：单独存储、不计入队列上限，最多保留 20 条，超了滚动删除最旧的并留日志。

## 后果

- 幂等键 `submission_operation_id` 在会话开始时生成一次、与扫描数据原子绑定、持久化后**永不重算**；
- 重试退避：指数退避（30s 起步、上限 15min），适用 429/5xx；400/403 转人工状态并屏幕标红；
- 放弃与未完成会话在固件层面严格区分：放弃=操作员主动、数据可能完整；未完成=非正常退出、数据必不完整。前者留档7天、后者留 20 条滚动。
