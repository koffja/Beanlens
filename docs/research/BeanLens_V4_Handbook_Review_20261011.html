BeanLens V4 手册增补评审：五槽重力方案验证、ESP32-S3 回归方案与结构遮光设计

研究日期：2026-10-11（下午增补）· 评审对象：output/beanlens/beanlens-v4-handbook.html（V401，2026-10-11 11:52 生成） 前置关系：本文增补上午的《BeanLens 硬件方案评审》（同目录），该报告评审的是 10-10 BOM（振动料斗+触发抓拍+HX711+ESP32 网络协处理器）。V4 已是再演进两代的方案，上午报告中多个结论的适用性需要重新对照。 用户裁决输入：认同 ESP32-S3 继续使用。

Executive Summary（执行摘要）

V4 是一次实质性进步：删除振动送料器（隔振问题随之消失——上午报告 F6 的最大结构担忧自动消解）、改五槽重力送料、连续取图+轨迹配对替代命令式触发抓拍（与上午报告 F2 建议的方向一致）、NAU7802 I²C 称重替代 HX711 位时序驱动（减轻 MicroPython 负担）、分阶段运行与内存控制专节（回应上午 F5）、对卷帘快门形变做了诚实披露（上午 F3 的口径被采纳）。接线表、两批采购、14 步装配、A–E 五阶段验收的质量都在线。

但增补研究抓出 V4 的四个新缺口与两个残留风险：

第一，吞吐缺口是硬的。手册自估总流量 25 颗/秒、每颗两面共需约 50 次分类/秒；而 K230 KPU 实测口径是 MobileNetV2 约 30–60ms/次（16–33 次/秒，社区数据，YOLO 含前后处理 180–220ms）。缺口 1.5–3 倍。手册”分阶段运行”的方向对，但 350–500g（约 2300–3300 颗）× 两面的集中分类需要 3–8 分钟排队消化——演示叙事必须按”流式采集+异步分类”表述，闸门节拍要按分类消化速度反推。

第二，出口速度未标定 + 30fps 不可依赖。按 V4 实际几何（视野高 67.5mm）重算卷帘拉伸：60fps 下行扫等效速度约 4.04m/s，静止释放情景豆末速 1.19m/s 拉伸 1.42×（可用），但出口若带 0.5m/s 初速拉伸升到 1.72×，近自由落体则 6 倍以上；30fps 时仅最理想情景勉强可用。60fps 是底线，压出口速度（刷条减速+可换导嘴+实测标定）是前置条件。

第三，环境光控制整体缺失。V4 照明节只定了灯与灰背景，没有暗箱/遮光设计，排障表没有环境光项，全文未出现”锁定曝光与白平衡”条款——而展厅射灯、人流遮挡、评委手机闪光都是真实干扰。这恰好是用户海洋板构想的杀手级用武之地：海洋板侧板把 2020 型材框补成半封闭箱体，一举解决遮光+结构+观感三件事。

第四，首版无网络与演示日叙事矛盾。V4 写 TF 卡 CSV、联网”后加串口网络模块”。但比赛演示的核心链路是”检测记录实时上 TasterMatrix staging”。用户认同保留 ESP32-S3——增补报告给出它在 V4 架构下的精确角色（串口网关+系统看门狗，非必需品而是演示日生命线）、接线方案与上电时序，以及”验证期先用 K230D 板载 WiFi、彩排期切 ESP32”的双路径策略。

残留两项：双摄并行”各 60fps”无公开实测（D1 必测，预案降分辨率）；裁图中转的内存细节（建议 JPEG 即时落盘中转，队列上限做背压）。

2. 主要发现（Main Analysis）

P1. 吞吐缺口：50 分类/秒的需求 vs 16–33 次/秒的能力

手册 05 节自己算了需求账：“总流量 25 颗/秒、每颗两面各分类一次，就需要约 50 次分类/秒。这是需求计算，不是 K230D 实测能力。”——这个诚实声明需要配上能力侧数据才是完整决策依据：

模型 K230 KPU 实测口径 等效吞吐 来源性质
YOLO 类（3.2MB kmodel，含缩放+推理+后处理） 180–220ms/帧 ~5 次/秒 社区实测帖 [31]
MobileNetV2 224×224 int8 30–60ms/次（社区通行口径） 16–33 次/秒 社区口径 [32]，待 D1 实测

即便 MobileNetV2 跑到乐观值，能力约为需求的 1/2 到 2/3；计入裁图、配对、队列开销后缺口更大。这不是要换硬件——而是要把三个既有设计拧成一套自洽的节拍：

  1. 闸门节拍按分类消化速度反推：手册放料”先试开到位后 150–300ms”是采集视角的初值。若每批实际放 50–100 颗（5 槽×密度×开闸时长），按 30ms/次×2 面=3–6 秒消化时间，则批次间隔应 ≥ 消化时间，或接受队列积压到关闸后集中处理。
  2. 采集-分类流水线化而非严格分阶段：手册六状态机的”4 分类”放在排空之后，实现上建议改为采集线程持续跑、分类 worker 低优先级异步消化队列（手册”队列有余量时，再开放下一批”已含此意，落实为生产者-消费者即可）。
  3. 演示叙事定稿：350–500g 全程 = 采集 2–3 分钟 + 分类排队 3–8 分钟（按 40–100ms/次折算 2300–3300 颗×2 面）。屏幕数字”爬升中”是可接受的演示节奏，但不要承诺”实时识别”；每批小份量模式（放 100 颗→等结果→再放）可给评委”准实时”体感。

附带约束：kmodel 加载约 1.2 秒 [31]，开机自检状态（状态 1）要把它计入。

P2. 出口速度未标定 + 帧率底线：30fps 不可依赖

V4 视野高 67.5mm、上沿在出口下 5mm。代入上午报告的拉伸公式（拉伸比 = 1/(1−v/v_scan)，v_scan = 视野高 ÷ 全帧读出时间）：

情景 视野内末速 60fps（读出≈16.7ms，v_scan≈4.04m/s） 30fps（读出≈33.3ms，v_scan≈2.03m/s）
a 出口静止释放（手册理想） 1.19 m/s 拉伸 1.42× 拉伸 2.45×
b 出口初速 0.5m/s（手册情景） 1.69 m/s 拉伸 1.72× 拉伸 6.1×（近失效）
c 近自由落体（280mm 落差） ~3.4 m/s 拉伸 6.4×（近失效） 拍不全

三个推论：

  1. 60fps 是底线不是目标。手册 B 阶段验收必须加一条”实测双路帧率 ≥60fps”（注意 GC2093 超配静默降级坑：看实测值不看配置值 [8]）。双摄并行各 60fps 目前只有”三路 CSI 硬件并行+官方三摄 demo”的间接佐证 [33][34]，无同型号双 60fps 实测——D1 必测，预案是降分辨率/ROI。
  2. 压出口速度是前置条件。手册已有的手段（对刷条减速、可换 10–14mm 导块、12mm 最后导嘴）之外，建议把”出口速度实测”做成打样验收项：方法可以是单槽临时装上下两对光电测时间差，或用已知帧率的录像逐帧位移折算。目标：出口初速 ≤0.3m/s（情景 a/b 之间）。
  3. 训练端配垂直拉伸增强（0.5–3×）依旧适用，让分类器直接认拉伸态的豆——V4 的排障表把”换传感器”列为最后退路，正确；拉伸增强是让”退路”大概率用不上的便宜保险。

P3. 环境光控制缺失：海洋板的杀手级用武之地

V4 在照明上只做了三件事：5000K/Ra≥95 恒定直流灯、扩散片斜照、灰背景。没有暗箱/遮光设计，没有”锁定曝光与白平衡”条款，排障表没有环境光项。对比 Codex 自己 10-08 的托盘方案文档（“遮外光的小箱……可锁定曝光与白平衡的近距离相机”），这是一处退化。展厅现实：顶射灯、邻展位灯光变化、围观人影、评委手机闪光——任何一项都能让自动曝光/白平衡漂移，连续取图下的表现是整批豆的颜色基准漂移（颜色类主判的直接威胁）。

补三件事：

  1. 海洋板侧板+顶板把 2020 框补成半封闭箱体：留出正面观察窗（亚克力）与背面检修口。18mm 海洋板同时提供遮光、结构阻尼、专业外观——用户的构想恰好补上 V4 最大的演示日风险。底部开孔走线+称重平台穿出（与底板保持 ≥5mm 间隙，载荷只经传感器——手册装配步骤 03 的要求保持不变）。
  2. 曝光/增益/白平衡全手动锁定写入固件需求：现场用灰卡/色卡校准后锁死，例行保存校准记录（也回应 Codex 10-08 文档的”迷你色卡”BOM 项——V4 采购表里色卡消失了，应找回）。
  3. 排障表加一行：“颜色基准漂移 → 检查环境光入射、曝光/白平衡锁定状态、灯的温升漂移”。

P4. 裁图中转的内存细节：队列上限需要落盘中转配合

手册的内存控制（少量帧、裁图独立缓存、队列上限）方向正确，但有一处未展开：350–500g 的整批豆（2300–3300 颗×2 面）的裁图不能驻留内存等待集中分类。按 224×224 裁图 RGB 计约 150KB/张，整批约 0.7–1GB——远超 128MB。落实方式：

  • 裁图产生即 JPEG 压缩（单张约 10–20KB）落盘 TF（整批约 50–130MB，TF 卡无压力）；
  • 内存队列只保留”待分类窗口”（如最近 200–400 张），分类 worker 从盘上批量读回消化；
  • 队列上限同时充当背压：积压超限时暂停下一批放料（手册已有此语义，补上盘上中转这一环即可闭环）。

P5. 网络与 ESP32-S3：演示日生命线的精确接线方案（用户裁决的落地）

V4 的立场（首版 TF 卡、联网后加、“不必因此恢复 ESP32 主控架构”）在验证期是正确的——D1–D3 少一个变量。但演示日的核心叙事是”检测记录实时上 TasterMatrix staging”（10-08 既定后端：device token 配对、telemetry 批量上报、WS 推送、锚定证据链），TF 卡拷贝演示链路是断的。用户认同保留 ESP32-S3，落地如下：

角色定稿：串口网关 + 系统看门狗（不是主控、不碰控制回路）

职责 实现方式 备注
WiFi telemetry ESP32-S3 连 staging，UART 从 K230D 收结果记录批量上报 K230D 的 UART 选脚注意手册 Pin 表：GPIO5/GPIO6（第 4/5 槽光电占用）恰是常见 UART 复用脚，手册已明示不复用——ESP32 接线前按立创现行引脚工具再核一遍可用 UART 脚位
心跳/看门狗 K230D 每秒发心跳；ESP32 超时未收到则屏显报警+上报 staging K230D 死机时演示不至于黑箱

断网兜底 ESP32 本地缓存最新批次；网络恢复补传 staging 热点+预采回放兜底不变

双路径时序（避免”新增硬件变成新故障源”）：

  • D1–D3（验证期）：按 V4 原案跑，无 ESP32。D1 顺带用 K230D 板载 WiFi（RTL8189FTV） 做一次联网冒烟（发几条假 telemetry 到 staging），确认 MicroPython 下网络与采集并发的稳定性——这是”板载 WiFi 直连”路径的证据。
  • D4（赛前彩排）：装 ESP32-S3 网关跑全链路。若 ESP32 链路任何环节掉链子，回退板载 WiFi 直连——两条路径共享同一份 telemetry 代码抽象（UART 口 vs 板载 socket 两个 driver）。
  • 采购：ESP32-S3 不进第一批（手册第一批清单保持纯净），放第二批或单独小单（¥30 级，随时可补）。

给评委的一句话口径：“视觉主控专机专用，网络与心跳由协处理器承担，故障域隔离。”——这句话在评委追问”为什么要两颗芯片”时是满分答案，也兑现了用户保留 ESP32-S3 的直觉。

P6. V4 已足够好的部分（免再议清单）

以下各项经增补核验，维持 V4 原案即可：NAU7802 选型（I²C 0x2A、静态读数、1kg 量程含平台/杯/样本的提醒）；MG90S 独立供电支路+限位开关+断电手动止料插片；五路光电”经过提示+排空辅助，不保证逐颗计数”的诚实定位；两批采购的降险顺序；14 步装配检查表；A–E 五阶段验收（“先证明没有漏检，再报告分类结果”）；“双面拍摄不等于完整 360° 表面检测”的口径；CSV 字段与 TasterMatrix 对接”先约定格式再实现接口”；CS11 镜头的六项核实清单（无完整规格前不按它打样安装件）。

3. 综合与洞察（Synthesis & Insights）

V4 与上午报告的关系可以一句话概括：上午报告指出的四个问题，V4 用自己的方式解决了两个半（触发架构、内存方向、隔振消解），剩下的一半（网络定位）由用户的 ESP32-S3 裁决补齐，而 V4 新引入的五槽架构带来了新的真实约束（吞吐、速度、环境光），三者都有不换器件的解法。

贯穿性的判断不变：这台装置是”时序机器”。V4 把时序问题从”触发的微秒级”（已消解）转移到了”吞吐的秒级”（分类消化）与”光学的小时级”（环境光/温漂）。风险等级实际上是下降的——秒级问题可以用节拍和排队吸收，而微秒级问题不能。

海洋板的角色从上午报告的”底板+配重”升级为”半封闭箱体的遮光壳”——这是本次增补最值钱的一条结构建议，因为它同时关掉了 V4 最大的演示日风险（环境光）和观感短板。

4. 局限与注意事项（Limitations & Caveats）

  • MobileNetV2 30–60ms 为社区通行口径，非本装置本模型实测；裁图尺寸、量化版本、前后处理都会移动这个数字。D1 以 nn_mobilenetv2 类示例实测为准。
  • 双摄并行各 60fps 无公开实测；拉伸比计算依赖读出时间近似（按帧率上限折算），GC2093 完整时序参数在 NDA 数据手册内。
  • 出口速度三情景是估算边界，真值取决于槽壁摩擦与刷条参数——打样后以实测替代。
  • 环境光风险的严重度依赖赛场条件，属工程判断而非已发生故障。
  • 本增补不改上午报告的推导公式与来源台账；新增来源见下。
