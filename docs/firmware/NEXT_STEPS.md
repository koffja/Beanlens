# BeanLens v1 开发：下一步行动清单

文档版本：0.1（2026-10-23，基于 ADR 0001–0005 与完整架构）

---

## 一、立即可做（不依赖任何联调）

### 1. BOX 固件基础框架搭建
**为什么**：UI 层（LVGL）+ 业务层目录结构可以先建,不依赖模型或网络。

**行动**：
- 按 `ARCHITECTURE-v1.md` §二分层架构创建目录：
  ```
  src/
    ui/          # LVGL 页面
    core/        # 业务逻辑
    capture/     # 采集与推理
  config/        # 配置文件
  tests/         # 单元测试
  ```
- 写 `core/config_manager.py`：读写 `~/.beanlens/config.json`（样品重量/队列路径）；
- 写 `core/scan_session.py` 最小版：定义 `ScanSession` 类 + `to_record_json()` 方法（输出硬编码假数据，16 类全 0）；
- 写 `core/queue.py` 最小版：`enqueue()` 写文件、`next_pending()` 读文件。

**出口标准**：造一条假 session → `queue.enqueue()` → 检查 `~/.beanlens/queue/<operation_id>.json` 文件存在且内容合法。

---

### 2. 双摄采集管线原型
**为什么**：CSI1/CSI2 触发连拍与时间戳配对是核心技术难点,需尽早验证。

**行动**：
- `capture/camera.py`：双摄 3 帧连拍 + 时间戳；
- `capture/pairing.py`：时间容差配对 + unpaired_count；
- 写测试：手投 10 颗豆 → 验证配对率 >80%。

**出口标准**：
- 逐颗手投 50 颗豆 → 配对成功率 >95%；
- 连续投 50 颗豆 → 配对成功率 >80%；
- 若 <80%,调整 `ΔT` 或改触发阈值再测。

---

### 3. YOLOv8n 16 类推理集成
**为什么**：模型是计数的基础,集成与性能测试需尽早。

**行动**：
- 加载模型 `beanlens-defect@1.3.0+ds20261001`；
- 对 PairedBean 的裁剪 ROI 做推理 → NMS → 输出 16 类计数增量；
- 写测试：手工标注 20 颗瑕疵豆 → 逐颗推理 → 检测准确率 >85%。

**出口标准**：每类至少 1 颗瑕疵豆,检测准确率 >85%（允许少量误分类,但不能全黑豆漏检）。

---

### 4. 会话状态机完整实现
**为什么**：状态机是固件主干,所有功能都依赖它。

**行动**：
- `core/scan_session.py` 完整版：7 态 + checkpoint（30 颗/5 秒）+ 断电恢复；
- `core/counting.py`：SCA 当量计算 + 预览计点；
- 写测试：状态转换完整性、checkpoint 触发、断电恢复、自检规则。

**出口标准**：
- 100 次状态转换（覆盖所有 7 态路径）→ 无异常；
- 扫描中断电 → 重启 → 恢复为 incomplete → 可查看/丢弃。

---

## 二、队列与本地验证

### 5. 队列管理完整实现
**为什么**：队列是数据持久化与重试的核心,需完整验证。

**行动**：
- `core/queue.py` 完整版：状态转换 + 重试退避 + 容量阈值 + 断电恢复；
- `core/report.py`：上报编排 mock 版（用本地测试桩模拟 200/400/403/429/5xx）；
- 写测试：入队/出队/状态转换/重试退避/容量触顶/断电恢复。

**出口标准**：
- 100 条记录入队 → 模拟各种响应码 → 断言状态与重试次数正确；
- 队列满触顶 → 阻断新扫描 → 模拟恢复 → 继续上传。

---

### 6. LVGL UI 完整实现
**为什么**：UI 是操作员交互的唯一入口。

**行动**：
- 待机页：显示「开始扫描」按钮 + 队列积压条数；
- 扫描中页：3 个大数字（豆粒总数/瑕疵豆数/配对不明）+「停止」按钮；
- 结果确认页：16 类列表 + 一类/二类点数 + 预览计点 +「本地保存」「放弃」按钮；
- 设置页：样品重量配置 + 队列管理入口 + 诊断入口；
- 诊断页：手动双摄预览（2fps）+ 检测框叠加。

**出口标准**：给非技术操作员演示一遍完整流程（开始 → 扫描 → 停止 → 查看结果 → 保存/放弃）→ 无需口头指导能完成。

---

## 三、集成测试与打磨

### 7. 完整扫描会话集成
**为什么**：端到端验证所有模块协同工作。

**行动**：
- 点「开始」→ `session.start()` → 启动采集管线；
- 投 50 颗豆 → 采集 + 配对 + 推理 + 计数；
- 点「停止」→ `session.stop()` → 跳转结果页；
- 结果页点「本地保存」→ `queue.enqueue()` → 进本地队列。

**出口标准**：
- 30 次完整扫描（每次 30–50 颗豆）→ 所有记录都成功入队 → 本地队列文件完整；
- 抽 10 条核对 `bean_count_total` / `defects[]` 与屏显一致。

---

### 8. 断电恢复完整验证
**为什么**：断电恢复是一等公民,必须端到端测试。

**行动**：
- 扫描中断电 → 重启 → 待机页横幅提示「未完成会话」→ 查看/丢弃；
- 队列积压时断电 → 重启 → 队列完整恢复 → 继续本地保存；
- 放弃会话断电 → 重启 → discarded 状态保留 7 天。

**出口标准**：
- 断电 5 次（扫描中/队列积压/放弃会话等场景）→ 每次重启后数据完整且状态正确。

---

### 9. 边界与异常测试
**为什么**：边界条件最容易暴露 bug。

**行动**：
- 16 类全 0（合法）；
- 单类 >30%（不拒收）；
- 配对不明 >20%（屏幕提示）；
- sum(16 类) > bean_count_total（固件自检拒绝保存）；
- 队列 100 条（触顶阻断）；
- checkpoint 频繁触发（验证 TF 卡写入延迟）。

**出口标准**：所有边界条件都有清晰提示,无崩溃/无数据丢失。

---

## 四、性能优化与文档

### 10. 性能测试与调优
**行动**：
- 双摄 3 帧连拍内存占用测试（≤ K230D 可用量）；
- 批量推理 N 值调优（初值 N≤8,实测后可能降低）；
- Checkpoint 频率调优（初值 30 颗/5 秒,实测 TF 卡延迟后可能调整）；
- 配对容差 ΔT 标定（初值 2 帧间隔,实测配对率后可能调整）。

**出口标准**：
- 连续扫描 100 次（每次 50 颗豆）→ 无 OOM / 无卡顿 / 配对率 >80%。

## 六、风险与缓解

| 风险 | 概率 | 影响 | 缓解 |
|---|---|---|---|
| 双摄配对率 <80% | 中 | 高 | §一.2 提前测试,不够就改 `ΔT` 或增加轨迹先验 |
| 模型 16 类准确率不足 | 中 | 高 | 与视觉侧早期对齐数据集覆盖度 + 标注质量 |
| K230D 内存不足（3 帧×双摄×全分辨率） | 低 | 中 | §四.10 实测后降分辨率或减帧数 |
| TF 卡写入寿命（频繁 checkpoint） | 低 | 低 | wear-leveling FS 或提高 checkpoint 间隔 |

## 七、P2 网络功能规划（延后评估）

**当前决策**：v1 暂不实施 C6 网络桥与实际上报功能（ADR 0003）。

**P2 重新评估**：
1. **C6 桥方案可行性**：ESP-IDF 固件开发成本、UART 协议调试周期、WiFi/HTTPS 适配复杂度；
2. **替代方案探索**：USB 转发（BOX 通过 USB 连接开发机/手机上传）、预置 WiFi 模块（非 C6）、蓝牙传输等；
3. **投入产出比**：v1 本地验证已覆盖固件主干 90%,网络功能的增量价值 vs 开发成本。

**延后不影响 v1 交付**：队列管理/幂等机制/断电恢复/状态机转换等核心逻辑在本地 mock 环境已完整验证,切换到实际网络上报时只需替换 `report.py` 的 HTTP 客户端实现。
