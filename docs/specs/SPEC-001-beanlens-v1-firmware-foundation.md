# SPEC-001: BeanLens v1 固件基础架构

**状态**: Ready for Implementation  
**创建日期**: 2026-10-24  
**相关 ADR**: ADR 0001, 0002, 0004, 0005

---

## Problem Statement

BeanLens K230D 生产现场需要一个可靠的咖啡生豆瑕疵检测固件,支持双摄采集、16 类瑕疵分类、本地队列管理与断电恢复。当前仅有硬件与模型原型,缺乏完整的固件主干、会话管理、队列持久化与异常恢复机制。

操作员需要通过 640×480 触屏完成：开始扫描 → 连续投豆 → 停止 → 查看结果 → 本地保存的闭环流程,并在断电后能恢复队列,不丢记录。

---

## Solution

构建 BeanLens v1 固件的核心架构,包含：

1. **双摄采集管线**：CSI1/CSI2 非硬同步双摄,通过时间戳+轨迹配对,3 帧连拍触发机制
2. **会话状态机**：7 态管理（pending/scanning/result_ready/queued/saved/discarded/incomplete）,支持 checkpoint 与断电恢复
3. **计数与规则**：16 类瑕疵分类（SCA 权威表）,豆粒总数不依赖模型,预览计点仅供参考
4. **队列管理**：TF 卡持久化,重试退避,状态转换,容量阈值
5. **LVGL UI**：3 页主交互（待机/扫描中/结果确认）+ 设置页,诊断页双摄预览

v1 简化：无批次关联、无证据图、无实时相机预览、无配网与配对、无 C6 网络桥（延后实施,队列逻辑用 mock 客户端本地验证）。

## User Stories

### 采集与计数
1. 作为操作员,我想点「开始扫描」后持续投豆,系统自动抓拍并计数,这样我不需要逐颗手投
2. 作为操作员,我想看到实时更新的豆粒总数/瑕疵豆数/配对不明数,这样我能确认设备正在工作
3. 作为操作员,我想点「停止」后计数立即冻结,这样我能确认当前批次的最终数据
4. 作为固件开发者,我需要双摄配对率 >80%,这样才能保证数据质量
5. 作为固件开发者,我需要豆粒总数 = 配对成功 + 配对不明,这样总数不会受模型漏检影响

### 会话管理
6. 作为操作员,我想在结果页看到 16 类瑕疵的详细分组列表,这样我能了解瑕疵分布
7. 作为操作员,我想看到一类瑕疵点数/二类瑕疵点数/预览计点,这样我能初步评估等级
8. 作为操作员,我想在结果页有「本地保存」和「放弃」两个选项,这样我能处理错投/洒豆的情况
9. 作为操作员,我想放弃会话时看到二次确认弹窗,这样我不会误操作
10. 作为操作员,我想放弃的会话本地保留 7 天,这样事后可以对账
11. 作为固件开发者,我需要结果页不能「继续扫描」补豆,这样 captured_at/duration_s 才能保持一致性

### 队列与重试
12. 作为操作员,我想点「本地保存」后记录自动进入队列,这样我能继续下一次扫描
13. 作为操作员,我想在待机页看到队列积压条数,这样我知道有多少记录待处理
14. 作为固件开发者,我需要队列由 mock 客户端在后台驱动状态转换,这样 v1 不依赖网络也能验证队列逻辑
15. 作为固件开发者,我需要队列持久化到 TF 卡,这样断电后能恢复
16. 作为固件开发者,我需要 mock 失败时按指数退避重试（30s 起步,上限 15min）,这样 P2 切真实网络时逻辑可直接复用
17. 作为固件开发者,我需要 mock 400 拒收的记录标记为 failed_rejected 并停止重试,这样操作员能人工修正
18. 作为固件开发者,我需要 mock 403 配额用尽的记录停止重试并提示操作员,这样不会无限排队
19. 作为固件开发者,我需要队列容量双阈值（100 条 且 500MB）,这样触顶时能阻断新扫描

### 断电恢复
20. 作为操作员,我想扫描中断电后重启能看到「未完成会话」提示,这样我知道上次发生了什么
21. 作为操作员,我想未完成会话能查看或丢弃,这样我能决定是否重新扫描
22. 作为固件开发者,我需要未完成会话标记为 incomplete 且不可保存入队,这样不会把不完整数据留作有效记录
23. 作为固件开发者,我需要每 30 颗或 5 秒 checkpoint 一次,这样断电最多丢 30 颗数据
24. 作为固件开发者,我需要用临时文件+原子 rename 写入,这样覆写中断不会得到半个 JSON

### 配对与规则
25. 作为固件开发者,我需要前摄与后摄时间戳差 ≤ ΔT（初值 2 帧间隔）才允许配对,这样不会把不同豆配对
26. 作为固件开发者,我需要一对一消费 track,这样同一豆不会被配对两次
27. 作为固件开发者,我需要落单 track 进入配对不明计数,这样总数能对上
28. 作为固件开发者,我需要配对不明率 >20% 时屏幕提示,这样操作员能调整豆路或光照
29. 作为固件开发者,我需要 assert sum(16 类) ≤ 豆粒总数,这样能及早发现计数 bug
30. 作为固件开发者,我需要 16 类当量按 SCA 表计算预览计点,这样操作员能现场参考
31. 作为固件开发者,我需要预览计点带「临时规则」角标,这样操作员知道这不是最终结果

### UI 与配置
32. 作为操作员,我想待机页显示队列积压条数,这样我能一眼看到设备状态
33. 作为操作员,我想扫描中页只有 3 个大数字+「停止」按钮,这样界面清晰不干扰
34. 作为操作员,我想设置页能配置样品重量（默认 350g,范围 300–400）,这样适配不同需求
35. 作为操作员,我想设置页能进入队列管理,查看/删除队列项,这样我能手动干预本地记录
36. 作为操作员,我想设置页能进入诊断页,手动开启双摄预览（2fps）,这样装调时能检查豆路

### 数据完整性
38. 作为固件开发者,我需要每条记录生成幂等键 `K230D:<序列号>:scan:<8位hex>`,这样重试时不会重复
39. 作为固件开发者,我需要幂等键在会话开始时生成并持久化,这样所有重试复用同一值
40. 作为固件开发者,我需要 captured_at 用本机时钟并打 metadata.clock_unreliable 标,这样 NTP 失败不阻断扫描
41. 作为固件开发者,我需要 operation_id 与扫描数据原子绑定,这样不会出现 ID 与数据不匹配

### 性能与资源
42. 作为固件开发者,我需要双摄 3 帧连拍（640×480）内存占用 ≤ K230D 可用量,这样不会 OOM
43. 作为固件开发者,我需要批量推理（N≤8 个 PairedBean）,这样内存可控
44. 作为固件开发者,我需要 checkpoint 触发条件可配置,这样实测后能调优
45. 作为固件开发者,我需要 TF 卡写入用 wear-leveling FS,这样延长使用寿命

## Implementation Decisions

### 架构分层
- **UI 层**（`src/ui/`）：LVGL 页面（待机/扫描中/结果/设置/队列管理/诊断）,v1 无需软键盘（配网延后）
- **业务层**（`src/core/`）：会话状态机（`scan_session.py`）、队列管理（`queue.py`）、配置管理（`config_manager.py`）、计数规则（`counting.py`）
- **采集层**（`src/capture/`）：双摄管理（`camera.py`）、时空配对（`pairing.py`）、检测调度（`detection.py`）、预处理（`preprocessing.py`）
- **持久化**：TF 卡 `~/.beanlens/` 目录（令牌、配置、队列、会话 checkpoint）

### 会话状态机（ADR 0004）
- 7 个状态：pending / scanning / result_ready / discarded / queued / saved / incomplete
- 转换规则：
  - pending → scanning（点「开始」）
  - scanning → result_ready（点「停止」）
  - result_ready → discarded（点「放弃」+二次确认）
  - result_ready → queued（点「本地保存」）
  - queued → saved（本地保存成功）
  - queued → failed_retriable（mock 模拟 429/5xx 场景,保留重试退避逻辑供 P2 切换真实网络时复用）
  - queued → failed_rejected（mock 模拟 400/403 场景）
  - scanning → incomplete（断电/崩溃）
- 每个状态对应的持久化文件：
  - scanning：`~/.beanlens/sessions/active/<session_id>.json`（checkpoint）
  - incomplete：`~/.beanlens/sessions/incomplete/<session_id>.json`
  - discarded：`~/.beanlens/sessions/discarded/<session_id>.json`
  - queued/saved/failed：`~/.beanlens/queue/<operation_id>.json`

### 双摄配对（ADR 0002）
- 采集方案：低分辨率常开前景判断（运动检测）→ 触发 3 帧短曝光连拍（640×480）
- 配对判据：
  - 只有 |timestamp_front - timestamp_rear| ≤ ΔT 才允许配对
  - ΔT 初值 = 2 帧间隔（写入 `config/capture_config.json`，实测后可调）
  - 一对一：同一 track 不能被两次配对消费
  - 落单进 unpaired_count
- 豆粒总数 = 配对成功数 + 配对不明数（不依赖 16 类模型）
- 自检规则：assert sum(16 类) ≤ 豆粒总数,违反直接报错不入队

### 计数与规则（ADR 0001）
- SCA 当量表（已核对）：
  - 类别一 6 项：全黑豆/全酸豆/咖啡干果/发霉豆/异物（各 1:1）、严重虫蛀豆（5:1）
  - 类别二 10 项：局部黑豆/局部酸豆（各 3:1）、带壳豆/漂浮豆/未熟豆/萎凋豆/贝壳豆/破碎破裂豆/干果皮壳（各 5:1）、轻微虫蛀豆（10:1）
- 预览计点：按 `sca-provisional` 规则版本计算,屏显带「临时规则」角标
- 记录体（本地队列 JSON,P2 上报时沿用）：只含 16 类计数,不含点值/等级（由平台重算）
- 模型 16 类 vs SCA 16 行映射：
  - `cut` 与 `broken` 合并上报为「破碎/破裂豆」
  - `fade`（褪色豆）SCA 表无对应,不上报,仅计入 `metadata.quality.fade_count`

### 队列管理（ADR 0004,v1 用 mock 本地客户端验证,无真实网络上报）
- 持久化：`~/.beanlens/queue/<operation_id>.json`（每条记录一个文件）
- 状态枚举：pending / saving / saved / failed_retriable / failed_rejected
- 重试退避：指数退避（30s * 2^retry_count,上限 15min）,适用 mock 模拟的 429/5xx 场景
- mock 响应码分类（`report.py` 本地测试桩模拟,保留与未来真实 HTTP 客户端一致的分类逻辑）：
  - 模拟 400（数据校验失败）→ failed_rejected,停止重试,屏幕标红
  - 模拟 401（令牌过期）→ 刷新令牌后重试
  - 模拟 403（配额用尽）→ failed_rejected,停止重试,提示「额度已用尽」
  - 模拟 429/5xx → failed_retriable,按退避重试
  - 模拟 200 → saved,删 record_json 只留元数据
- 容量双阈值：条数 ≤100 且 证据图总量 ≤500MB（v1 无图,此项预留）,触顶阻断新扫描

### 幂等与原子性（ADR 0004）
- 幂等键格式：`K230D:<device_id>:scan:<8位hex>`（session 开始时生成,持久化后永不重算）
- 400 拒收后可改数据重报,但复用同一 operation_id（服务端未落库,同 ID 重发不会重复）
- 原子写入：临时文件 + rename + 保留 .prev（覆写中断不会得到半个 JSON）
- Checkpoint 频率：每 30 颗或每 5 秒,先到先写

### v1 简化（ADR 0005）
- **无批次关联**：`form_config.sample_ids` 用 `BL-LOCAL-xxxx` 本地占位,`metadata.lot_id` 整字段省略
- **无证据图**：`metadata.evidence_images` 整字段省略,队列简化为只存 JSON
- **无实时预览**：扫描中页无相机预览（避 Display 与 sensor 流冲突）
- **无配网与配对**：v1 不做 WiFi 配网、二维码配对、6 位数字码配对,相关 UI 页面不实现
- **无 C6 网络桥**：v1 暂不实施 C6 桥与网络上报功能（延后评估,`report.py` 用 mock 客户端模拟上报响应）

### 配置文件
- **`config/capture_config.json`**：
  - `csi1/csi2`：分辨率/帧率
  - `roi_queue_max`：3（每路最多 3 个 ROI）
  - `time_pair_tolerance_ms`：null（待实测）
  - `motion_threshold`：25
  - `trigger_cooldown_ms`：50
- **`config/rules_sca_provisional.json`**：
  - `rule_version`："sca-provisional"
  - `equivalents`：16 类 → 当量 map
  - `category1/category2`：类别枚举数组
- **`~/.beanlens/config.json`**：
  - `sample_weight_g`：默认 350
  - `queue_path`
  - （WiFi 配置延后至 P2）

## Testing Decisions

### 测试原则
- **只测外部行为,不测实现细节**：测试模块的公开接口与状态转换,不依赖内部实现
- **优先高层接缝**：优先在业务层测试（会话状态机、队列管理）,采集层用 mock
- **断电恢复是一等公民**：所有持久化模块必须有断电恢复测试

### 需测试的模块
1. **会话状态机**（`core/scan_session.py`）
   - 状态转换完整性（7 态覆盖所有转换路径）
   - Checkpoint 触发（30 颗、5 秒、手动停止）
   - 断电恢复（incomplete 状态、元数据完整性）
   - 自检规则（sum(16 类) > 豆粒总数 时拒绝）

2. **队列管理**（`core/queue.py`）
   - 入队/出队/状态转换
   - 重试退避（指数退避上限、错误码分类）
   - 容量阈值（100 条触顶、500MB 预留）
   - 持久化完整性（原子写入、.prev 备份）
   - 断电恢复（队列完整性、状态一致性）

3. **双摄配对**（`capture/pairing.py`）
   - 时间容差配对（ΔT 内配对成功、超 ΔT 进 unpaired）
   - 一对一消费（同一 track 不被两次配对）
   - 配对率计算（>80% 正常、<80% 提示）
   - 边界：单侧丢帧、极快速豆、触发阈值调整

4. **计数规则**（`core/counting.py`）
   - SCA 当量计算（16 类 → full defect）
   - 类别分组（一类 6 项、二类 10 项）
   - 模型类 → SCA 行映射（`cut`+`broken` 合并、`fade` 不上报）
   - 预览计点（带角标、与平台侧可能不一致）

5. **配置管理**（`core/config_manager.py`）
   - 读写 `config.json`（重量/队列路径）
   - 配置缺失时默认值

### 测试先例（参考已有测试模式）
- 状态机测试：枚举所有状态转换,断言前置条件与后置状态
- 持久化测试：写入 → 断电模拟（删临时文件）→ 恢复 → 断言数据完整
- 配对测试：生成合成 track（已知时间戳）→ 配对 → 断言结果
- 队列测试：造 100 条记录 → 批量入队 → mock 客户端模拟响应 → 断言状态与计数

### 集成测试关键用例
- **端到端扫描**：开始 → 投 100 颗豆 → 停止 → 本地保存 → 断言记录与队列状态
- **断电恢复**：扫描中断电 → 重启 → 断言 incomplete 提示 → 丢弃 → 新扫描成功
- **队列满重试**：100 条记录积压 → mock 切到成功响应 → 断言全部转为 saved
- **配对率低告警**：调低 ΔT → 配对率 <80% → 断言屏幕提示

## Out of Scope

### v1 不做（延后到 P2）
- 批次关联（依赖平台 `/api/device/lots` 端点）
- 证据图上传（裁图+清晰度排序+落盘+上传管线）
- 实时相机预览（Display 与 sensor 流共存）
- 设备配对与配网（二维码/数字码配对、WiFi 软键盘配网、softAP web 配网）
- C6 网络桥与真实网络上报（UART 协议+WiFi STA+HTTPS 代发,v1 用 mock 客户端验证队列逻辑）
- 轻量数豆模型（独立「豆/非豆」二类检测,当前用前景+轮廓过渡）

### 明确不做
- 硬同步双摄（硬件不支持）
- 操作员手动逐颗投豆模式（只做连续投料）
- 多语言界面（v1 只中文）
- 触摸手势（只支持点击,不支持滑动/缩放）
- 远程固件升级（v1 手动刷 TF 卡）

## Further Notes

### 未决事项（需实测标定）
1. **时间配对容差 ΔT**：ADR 0002 初值 = 2 帧间隔,实测后写入 `capture_config.json`
2. **Checkpoint 频率优化**：30 颗/5 秒是初值,实测 TF 卡写入延迟后可能调整
3. **批量推理 N 值**：初值 N≤8,实测内存占用后可能降低

### 依赖外部条件
1. **模型**：YOLOv8n 16 类（beanlens-defect@1.3.0+ds20261001）可用
2. **硬件**：K230D BOX + 双摄 + TF 卡 + LVGL 触屏已就绪
3. **平台侧**（v1 暂不依赖）：配对端点/记录端点/令牌端点延后对接

### 风险与缓解
- **风险**：双摄配对率 <80% → **缓解**：实测后调 ΔT 或增加轨迹先验
- **风险**：模型 16 类准确率不足 → **缓解**：与视觉侧早期对齐数据集质量
- **风险**：TF 卡写入寿命（频繁 checkpoint）→ **缓解**：wear-leveling FS 或提高 checkpoint 间隔

### 下一步行动
见 `docs/firmware/NEXT_STEPS.md` 完整清单,优先级：
1. 基础框架搭建（目录+配置管理+会话最小版+队列最小版）
2. 采集管线（双摄 3 帧连拍+时间戳配对）
3. YOLOv8n 推理集成
4. 完整扫描会话集成
5. 断电恢复+队列重试
6. UI 打磨+诊断页
