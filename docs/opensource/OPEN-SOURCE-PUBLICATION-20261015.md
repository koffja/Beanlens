# BeanLens 开源发布切分方案

日期：2026-10-15（Asia/Shanghai）。状态：**发布规划，未执行任何公开操作**。本文档供后续参考与执行核对；未创建公开仓库，未做任何对外披露，不构成本文档之外任何内容的许可授权。

## 1. 目的与定位

- 决策背景：用户决定 BeanLens（豆鉴）未来以开源方式公开，目标是建立信任与声浪，为用户的解味视界项目导流。
- 定位打法：豆鉴作为**开源工具层**（初筛＋取证＋记录），解味视界作为**产品层**（风味/杯测侧）。开源工具的批次记录经数据协议流入产品，开放越充分，产品的入口价值越大。
- 前提说明：解味视界之名未出现在本仓库任何文档中。本方案按"与 Taster-Matrix 同向的风味/杯测侧产品"理解；两者在公开叙事中如何命名、如何互相提及，属未决项（见第 8 节），正式发布前须由用户确认。
- 总原则沿用项目既有结论：**叙事围绕可验证验收，而不是承诺**（见 `docs/research/BeanLens_Research_20261011.html` 发现六、`docs/firmware/BRINGUP.md`）。开源发布同样适用：先有可复核的东西，再公开。

## 2. 发布时机闸门（满足前不开仓）

按顺序全部满足才启动公开：

1. **实物里程碑**：至少完成 `docs/firmware/BRINGUP.md` 中"两板各自显示＋UART 握手"，进一步目标是单槽联调跑出一批**真实批次记录**（含证据裁图与称重读数）。发布物至少包含：一段运行视频、一条完整证据链样例、一份批次记录样例。
2. **竞赛披露检查（硬闸门）**：若豆鉴参加任何赛事（历史研究涉及 wtcc-2026，见 `docs/research/` 两份参赛文档），必须先核实该赛事规则中"赛前公开披露"条款。开源等于**永久、不可撤回的公开披露**，开仓时间不得早于规则允许的时点。结论与依据记入本文档第 8 节未决项，不得凭印象跳过。
3. **协议可发布**：`docs/firmware/PROTOCOL-v0.1-DRAFT.md` 补齐字段表、测试向量和超时标定后定稿。协议是豆鉴与解味视界之间的连接叙事点，发布时必须具体可读，不能停在草案。
4. **基线状态如实**：`config/hardware-baseline.json` 发布时保留真实核验状态；已实测的条目改为已核验并记录方法，未实测的保留"拟定"字样。不为了好看把拟定改成已验证。

## 3. 仓库切分清单

当前仓库 `.gitignore` 已排除数据集、训练产物、权重、厂商资料盘和虚拟环境，git 内已提交内容大体干净。但**不建议把本仓库直接转公开**：一是 `docs/` 内含内部交接、研究历史与商业/参赛策略；二是 git 历史一旦公开即随内容一并公开，日后误提交无法收回。正确做法是**新建独立公开仓库，按下表逐项拷贝**。

### 3.1 进入公开仓库

| 内容 | 来源路径 | 说明 |
|---|---|---|
| K230D 应用固件 | `firmware/k230d/` | 代码成形后进入；含目录内 AGENTS.md 可一并公开（体现开发纪律） |
| ESP32-C6 应用固件 | `firmware/esp32c6/` | 同上；`sdkconfig` 生成物不进（已被 .gitignore 覆盖），提供 `sdkconfig.defaults` 模板 |
| 通信协议 | `shared/protocol/`、`docs/firmware/PROTOCOL-v0.1-DRAFT.md` | 按 2.3 定稿后以正式版本号发布 |
| 验收路线 | `docs/firmware/BRINGUP.md` | 工程纪律的核心展示，随验收进度同步 |
| 硬件基线 | `config/hardware-baseline.json` | 按 2.4 如实标注状态 |
| 硬件设计文档精选 | `docs/hardware/` 中当前版本手册、BOM（CSV/JSON）、装配图册、闸门/对射/采购核查说明、对应 validation JSON | 只带**当前版本**（V4.5/V4.6 系），历史快照与被替代方案（V4.3/V4.4 旧图、旧 BOM）不进，避免误用 |
| 顶层 README 与安全声明 | 新写 | 见 5.2 审计清单第 4 条 |

### 3.2 不进入公开仓库（排除项与理由）

| 内容 | 来源路径 | 理由 |
|---|---|---|
| 数据集与训练产物 | `datasets/`、`runs/`、根目录两个 Roboflow 数据集目录及 zip、`*.pt`、`*.onnx`、`*.kmodel` | 用户数据资产；来源与许可映射未整理（未来若公开数据，须先按规范记录许可、来源和标签映射） |
| 正点原子资料盘 | `docs/【正点原子】DNK230D开发板资料盘(A盘)/` | 厂商版权资料，不得再分发。公开仓库只放官方 wiki 链接 |

## 4. 许可方案（建议，最终由用户决定）

| 层 | 建议 | 备选与差异 |
|---|---|---|
| 代码（固件、可公开脚本） | **Apache-2.0**（首选：含专利授权与 NOTICE 机制，对涉及 K230/nncase 生态的硬件项目更稳妥） | MIT 更简单，但无明示专利授权 |
| 硬件设计（手册、图纸、BOM 说明） | **CERN-OHL-W**（推荐起步：允许商业再利用但要求署名与状态保留，利于扩散） | CERN-OHL-S 强互惠，衍生设计必须同样开源；若担心被闭源商业克隆选 S。两者差异发布前向用户讲解后再定 |
| 文档 | **CC BY-SA 4.0** | CC BY 4.0 更宽松，不要求衍生文档同许可 |
| 数据集 | 暂不发布，无许可决定 | — |

补充：BOM 中的型号、价格等属事实性数据，许可对纯事实约束有限，公开即视为接受被引用；若在意，采购表中的供应商联系方式等商业信息应在发布版中剔除。**豆鉴/BeanLens 名称与任何 logo 不随上述内容许可授权**，他人复刻需另行获得名称使用授权——发布 README 中写明一句即可。

## 6. 发布战役要素（简要）

- 发布是一次**战役**不是丢仓库：视频、文章、仓库三件套同日上线，而不是先转公开等涨星。
- 受众区分：创客平台（GitHub、Hackaday 类）看开源硬件工程叙事；咖啡社区（烘焙商、Q 验豆师、比赛选手）看"验货有据可查"的实用叙事。两套文案，一个仓库。
- 连接叙事的核心一句：开源的是豆鉴工具，批次记录经公开协议流入解味视界形成风味档案——让开放成为产品入口，而不是产品广告。

## 7. 后续执行顺序建议

1. 日常开发按 `docs/firmware/BRINGUP.md` 推进，无需为开源改变节奏。
2. 低成本先做：将 `docs/A1-6-2F/` 加入 `.gitignore`；确定公开仓库命名与账号；协议草案升级。
3. 到达第 2 节闸门后：按第 3 节清单建公开仓库、跑第 5 节审计、按第 6 节发布。
4. 每次公开内容的增量更新，同步回写本仓库对应主文档，保持两侧版本可追溯。
